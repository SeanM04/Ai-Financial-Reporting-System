Two problems surfaced while making these changes. Turning CSRF back on would have broken every real upload with a 500 error, because the upload view read the request body after the CSRF check had already consumed it; a new test caught it and the view was fixed. The browser also gave AI requests 180 seconds, the same as the backend's worst case, so it could give up just before a report finished. It now waits 300 seconds, matching the server.

Part 2

How a request is checked now

Every API call passes these checks in order. The first one that fails decides the response. Before these changes, most report endpoints went straight to step 6.

  1. 1

    HTTPS and host name

    In production, plain HTTP is redirected to HTTPS and requests for host names outside ALLOWED_HOSTS are refused. The health check is exempt so uptime monitors keep working.

    301 redirectDEBUG=False only
  2. 2

    CSRF token and origin

    Any request that changes something must send the csrftoken cookie back in an X-CSRFToken header, and its Origin must be trusted. The frontend does this automatically. Signing in is the only exemption, since no token exists yet.

    403POST, PUT, DELETE
  3. 3

    Signed in

    Every report, upload and AI endpoint needs a session. Only sign-in, the health check and a test ping are open.

    401403 on some DRF routes
  4. 4

    Allowed to see this report

    The report must belong to the user, or the user must be staff. Anyone else gets "Report not found", so the reply doesn't confirm that the report exists.

    404report routes
  5. 5

    Within the rate limits

    Sign-in is blocked after repeated failures, and AI requests are capped per user per hour. The reply says how many minutes to wait and sets Retry-After.

    429sign-in and AI routes
  6. 6

    The endpoint runs

    For AI work it first counts the request against the daily quota, then calls OpenAI with a 60-second timeout. If the quota is used up or OpenAI fails, a rule-based report is built and clearly labelled.

    200or labelled fallback
  7. 7

    Errors leave nothing behind

    With DEBUG=False, any 500 response is logged in full on the server and replaced with a generic message for the browser. 4xx and 503 messages are kept, because they tell the user what to fix.

    500 genericDEBUG=False only

Part 5

Settings and shared state

The two settings files had drifted apart, for example in their DRF defaults and their DEBUG defaults. Everything except the database now lives in one shared file, so security settings can't differ between SQLite and PostgreSQL.

manage.py · wsgi.py · asgi.py · celery.py
        │
        └── financial_analytics/env.py      loads backend/.env, then picks:
              ├── settings_postgres   when DB_NAME or DATABASE_URL is set
              └── settings_sqlite     otherwise (local development, DEBUG on by default)
                     │
                     └── both import settings_base.py   everything except DATABASES

When DEBUG=False

  • Startup fails unless SECRET_KEY is a real generated key
  • HTTP redirects to HTTPS (health check exempt)
  • Session and CSRF cookies are HTTPS-only
  • HSTS on, starting at 1 hour; raise it once HTTPS is confirmed
  • 500 responses hide their details

When BEHIND_PROXY=true

  • Trusts nginx's X-Forwarded-Proto header, so HTTPS is detected correctly and the redirect doesn't loop
  • Uses X-Forwarded-For as the client address for sign-in limits

Origins

  • CORS_ALLOWED_ORIGINS: who may call the API
  • CSRF_TRUSTED_ORIGINS: who may send POSTs; defaults to the CORS list, which includes the Vite dev server on port 5173
Before

Each server process had its own memory cache

  • Reports were copied into each process and kept for up to 7 days
  • An edit made through one process was invisible to the others
  • The "one regeneration at a time" lock only worked within one process
Now

One source of truth, one shared cache

  • Reports are always read from the database
  • Rate limits, quota counters and locks live in a shared cache: a database table created by migrate, or Redis when REDIS_URL is set
  • The AI usage page now shows real numbers, because the counters are finally being written

Part 9

Still open

  • promptsShared prompts can be changed by any report owner. Regenerating a section updates the shared prompt module, and "save master prompt" overwrites the shared dataset prompt, while the direct prompt editors are staff-only. Decide whether that is intended.
  • scaleReport generation still runs inside the upload request. The timeouts now line up, and threaded workers keep one slow upload from blocking others, which is fine for a small team. Heavier use needs a background job queue.
  • frontendThe TypeScript check fails on five existing errors in PromptReportSplitPane.vue, so builds use build-only for now.
  • frontendThree frontend calls still hit old endpoints (report metrics, trends and benchmark) that read the empty legacy tables and can only return 404. The AI status panel also calls a wrong path (/api/analytics/ai/… instead of /api/ai/…).
