Part 1

Architecture

In development two processes run. The Vite dev server serves the Vue app and forwards every /api/* request to Django. Django does all the work in a single request: it checks the user, validates the upload, calls OpenAI, and stores the report in PostgreSQL. No background worker or Redis is needed. In production nginx and Gunicorn take the place of Vite and the Django dev server (see DEPLOYMENT.md).

Frontend, frontend/src

  • views/ holds the pages: Login, Dashboard, Upload, Reports, Report detail, Analytics, Settings, Prompt Studio
  • services/api.js makes every backend call through one Axios client and adds the CSRF header to changing requests
  • router/index.ts sends every page except /login to the login screen until a session exists

Backend, backend/analytics

  • urls.py maps every route under /api/
  • api/ holds the request handlers; api/access.py holds the shared sign-in, ownership and rate-limit checks
  • Much shared logic still lives in the large views.py; services/ holds the prompt registry, prompt modules, report store, cleanup and branded PDF

Settings

  • financial_analytics/env.py loads backend/.env and picks settings_postgres when DB_NAME is set, otherwise settings_sqlite
  • Both import settings_base.py, which holds everything except the database
  • backend/.env.example lists every setting, including the OpenAI key, rate limits and production switches
Part 2

From upload to report

This is the path taken by POST /api/simple-upload/, the upload route the frontend uses. Each step lists the code that runs and the tables it touches. All tables are prefixed analytics_ except Django's own.

Sign in
  1. 1

    Sign in and get a session

    The login page posts the username or email address and the password to POST /api/simple-login/. The backend tries the input as a username, then as an email. After five failures for one account from one address, sign-in is locked for 15 minutes. On success login() sets the session cookie and a fresh CSRF cookie. On each page change the router asks GET /api/auth/me/ whether the session is still valid.

    api/auth.py · simple_login_viewauth_userdjango_sessiondjango_cache
Upload and check
  1. 2

    Pick a dataset type and send the file

    On the Upload page the user chooses one of three dataset types (WACC, Money Market or Financial Instruments) and can also set the template, sections, length and detail level. The file goes up as multipart form data with the CSRF token in the X-CSRFToken header. The request must come from a signed-in user and counts towards that user's hourly AI limit (30 by default).

    views/UploadView.vueservices/api.js · /simple-upload/api/access.py
  2. 3

    Validate the file and its type

    Returns a 400 error for any of these: no file, no dataset type, a name not ending in .json, bytes that aren't UTF-8, or JSON that won't parse. Then comes the type check. Every key and text value in the file is scanned against six keyword groups for each type. The file passes only if it matches at least two groups and scores highest for the type the user picked.

    api/uploads.py · _validate_dataset_type
  3. 4

    Normalize the data and find a name and period

    The original JSON is kept untouched. An analysis copy is built beside it: a top-level array becomes {records, record_count}, and an older Dashboard-style file is flattened. The code then searches up to six levels deep for a name key (bank_name, company, entity…) and a period key (period, asOf, date…). If none is found, it uses "Financial Dataset" and "Unknown Period".

    views.py · normalize_json_for_analysisviews.py · extract_entity_metadata

Build the prompt
  1. 5

    Decide which sections the report will have

    The dataset type picks a default template unless the upload named one. The report prompt registry turns that template into an ordered list of section keys. A WACC report, for example, gets executive_summary, wacc_analysis, financial_ratios, risk_assessment, benchmark_comparison and recommendations.

    services/report_prompt_registry.pyreportconfiguration
  2. 6

    Split the analysis prompt into one prompt per section

    The prompt for the chosen dataset type is loaded from the database and cut into [SECTION:key] … [/SECTION] blocks. A section with no block borrows the text of its prompt module. The blocks are then joined back into the master prompt stored with the report.

    services/prompt_module_store.pyanalysispromptpromptmodule
  3. 7

    Save a placeholder and update the prompt modules

    A report row owned by the uploader is created right away with status processing and progress 35, under a new UUID that also serves as the task id. Next, every section prompt that differs from its prompt module's current text is saved onto that module as a new version, so each section of the report can later show which prompt wrote it.

    services/report_store.py · save_reportpersistedreportpromptmodulepromptmoduleversion
Generate
  1. 8

    Scan the numbers (no AI)

    The code walks the JSON, records every numeric field with its path, and tags it as revenue, profitability, risk and so on. The result is stored as ai_analysis and gives the report a structured summary even when the AI step fails.

    views.py · perform_initial_ai_analysis
  2. 9

    Ask OpenAI for every section in one call

    The call is first counted against the daily quota (OPENAI_DAILY_QUOTA_LIMIT, 1,000 by default). Then one chat completion runs in JSON mode. The system prompt combines the analyst instructions, a summary of the data, the full JSON (cut off at 14,000 characters) and the per-section instructions. The model comes from OPENAI_MODEL (default gpt-4o-mini), with up to 4,096 output tokens, a 60-second timeout and up to two retries. The reply must be {"sections": [...]}, with one item for each section key.

    views.py · generate_comprehensive_ai_analysisservices/dynamic_report_builder.py (fallback)django_cache
Store and trace
  1. 10

    Overwrite the placeholder with the finished report

    The same row is saved again with status completed, the sections in comprehensive_analysis, and ai_error when AI was unavailable.

    persistedreport
  2. 11

    Record where each section came from

    Each section gets a trace block naming its prompt module, version, model and confidence: the model name and 0.85 for AI output, or "fallback" and 0.50 for rule-based text. One mapping row per section is created or updated, with hashes of the content.

    prompt_module_store.py · annotate_report_sectionsreportsectionmapping
  3. 12

    Return the report

    The whole report goes back in the upload response. GET /api/tasks/{id}/ also exists for polling, but it only reads the status field from the report row.

    api/uploads.py · simple_task_status_view

Steps 2 to 12 all happen inside one HTTP request. OpenAI's worst case is about three minutes (three 60-second attempts), and the browser, Gunicorn and nginx each wait up to 300 seconds, so a slow reply ends in a labelled fallback report rather than a dropped connection.

Part 2b

What the AI step can return

Step 9 always produces a report, and the report always says whether AI wrote it.

SituationSections savedFlagged as AIWhat the user sees
Key set, OpenAI returns usable JSON AI-written sections, traced to the model ai_enhanced: true "Report generated from your analysis prompt"
No OPENAI_API_KEY Rule-based sections built from the data, traced as "fallback" ai_enhanced: false A warning that the key isn't configured, also stored as ai_error
The call errors, times out, hits the OpenAI quota or returns no sections Rule-based sections, traced as "fallback" ai_enhanced: false A warning with the reason; warning_code is openai_quota_exceeded for quota problems, otherwise ai_unavailable
The app's daily limit is reached Rule-based sections, traced as "fallback" ai_enhanced: false "The daily limit of 1000 AI requests has been reached. It resets at midnight UTC."

Regenerating a section or a whole report works differently. A rule-based result never replaces existing text. When AI is unavailable those requests return an error with the reason, and the report stays as it was.

Part 3

After the report exists

Every report belongs to the user who uploaded it. Users only see and open their own reports; staff can open any report, including old ones with no owner. Anyone else asking for a report gets "Report not found".

Read and list

GET /api/simple-reports/ lists the user's reports (staff also see unowned ones). GET /api/simple-reports/{id}/ returns one report, read straight from the database.

Rewrite one section (Prompt Studio)

POST /api/simple-reports/{id}/sections/{key}/regenerate/ takes an edited prompt of 3 to 12,000 characters and counts towards the hourly AI limit. A lock in the shared cache returns 409 if that section is already regenerating. It saves the prompt as a new version of the section's prompt module, asks the AI for that one section, adds the change to section_versions inside the report, and updates the mapping row.

Export

GET /api/simple-reports/{id}/export/?format= accepts json, pdf, csv, word or excel. The PDF is built with ReportLab and has a branded cover and contents page. Word uses python-docx and Excel uses openpyxl.

Archive, restore, delete (staff)

POST /api/reports/manage/bulk-action/ acts on several reports at once. Archiving sets is_archived; deleting removes the row and its section mappings. Every action writes an audit log row.

Retention cleanup

Deletes reports older than the user's retention setting (default 90 days; the unit can be days, weeks or months). Users clean up their own reports; staff also clear unowned ones. Run it from the app with a dry-run preview (/api/cleanup/) or with python manage.py cleanup_old_data, which DEPLOYMENT.md schedules nightly with cron.

Edit the master prompts (staff)

The five dataset analysis prompts can be edited, saved and reset to their defaults through /api/analysis-prompts/. A report's owner can also save its edited sections back as the dataset prompt (…/save-master-prompt/), which changes it for everyone.

Part 4

Database schema

A PostgreSQL database, financial_analytics, managed through Django's ORM and six migrations. Without DB_NAME in .env, local development uses the SQLite file backend/db.sqlite3 with the same schema. The models come from two generations of the design. The current app writes only the live tables. The legacy tables still exist and still have endpoints, but the upload flow never fills them.

Legacy tables

These six tables come from the first design: an upload is parsed into a dataset, which gets metrics, insights and a report, processed in the background by Celery. They are still served by /api/upload/ and the /api/reports/{id}/metrics/-style endpoints, but the frontend never uploads through that route, and Celery isn't part of the current setup. Retention cleanup still deletes old upload rows here, and their child rows go with them.

Part 5

Known limitations

  • uploadEvery upload needs a dataset type, and the file must pass the keyword check. The bundled sample_financial_data.json (bank accounts and a summary) fails for all three types, so test with a real WACC, money market or instruments file.
  • speedThe whole pipeline runs inside the upload request. A response can take up to about three minutes and holds a server thread meanwhile. Heavier use needs a background job queue.
  • promptsShared prompts can be changed by any report owner. Regenerating a section saves the edited prompt onto the shared prompt module, and "save master prompt" overwrites the shared dataset prompt. Both affect everyone's next report, while the direct prompt editors are staff-only.
  • frontendThree frontend calls point at legacy endpoints. api.js still requests report metrics, trends and benchmark data from tables the upload flow never fills, so they return 404. The AI status panel calls /api/analytics/ai/… instead of /api/ai/….
  • frontendThe TypeScript check fails on existing errors in PromptReportSplitPane.vue. Build with npm run build-only until they are fixed.
  • storageEach report stores the uploaded file twice (original and normalized), up to 50 MB each, and the row is rewritten on every edit. The retention cleanup keeps growth in check.
